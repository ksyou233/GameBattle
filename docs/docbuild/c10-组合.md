#### 2.2.8 组合模式（Composite）

**模式意图**：将对象组合成树形结构以表示"部分—整体"的层次结构，使得用户对单个对象和组合对象的使用具有一致性[1]。

**本项目面临的问题**：技能系统里既有单体技能（火球术、旋风斩、穿透射击），也有多段连招（裂地三连斩 = 三段斩击依次打出）。如果为"连招"单独设计一套调用方式，战斗循环里就必须判断当前这一招是什么：

```cpp
// 反面写法（本项目未采用）
if (isCombo(skill)) {
    for (auto& part : skill.parts) {
        part.cast(caster, target);      // 还要考虑 part 本身又是连招的情况 → 递归
    }
} else {
    skill.cast(caster, target);
}
```

这样的调用方需要了解"连招"的内部结构，而且连招里再嵌套连招时还需自己处理递归。一旦后续出现"复合技能包含若干个连招"的需求，这段判断还会继续膨胀。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 抽象构件 Component | `Skill` |
| 叶子 Leaf | `AttackSkill`、`HealSkill` |
| 容器 Composite | `ComboSkill` |
| 客户端 Client | `Battle::actOnce()` |

**实现要点**：`ComboSkill` 既是 `Skill`（对外统一），又持有若干 `Skill`（对内递归），因此连招里可以继续嵌套连招，自然形成一棵技能树：

```cpp
class ComboSkill : public Skill {
public:
    void execute(Combatant& caster, Combatant& target, EventBus& bus) override {
        // 组合模式的价值：这里不需要区分"子技能是单体还是连招"，
        // 一律调 execute() —— 对单个对象和组合对象的使用具有一致性。
        for (const auto& part : parts_) {
            if (!target.alive()) break;      // 目标已阵亡，连招中断
            part->execute(caster, target, bus);
        }
    }
private:
    std::vector<std::unique_ptr<Skill>> parts_;   // 子技能列表（树形结构的"子节点"）
};
```

于是战斗循环里只需要一行代码，既不需要判断技能类型，也不需要处理递归：

```cpp
skill->execute(actor, *target, bus_);
```

递归由多态自然完成 —— 这正是组合模式"让客户端忽略单个对象与组合对象的差别"的核心价值[1]。这一做法也印证了面向对象设计中"**优先使用对象组合，而不是类继承**"的基本原则[4]：技能树的层次关系是由"持有子技能"这一组合关系表达的，而不是靠在继承体系里为每一种技能搭配派生一个子类。

**本项目中实际使用的四个连招**：

| 连招名 | 组成 | 归属 | 特殊效果 |
|--------|------|------|---------|
| 裂地三连斩 | 斩击·壹 → 斩击·贰 → 斩击·叁 | 战士大招 | 第三段有 50% 概率眩晕 |
| 冰火两重天 | 烈焰冲击 → 寒冰禁锢 | 法师大招 | 第二段 100% 冰冻 |
| 疾风三连射 | 第一箭 → 第二箭 → 第三箭 | 射手大招 | 三段伤害倍率递增 |
| 暗影吐息 | 暗影冲击 → 龙息 | BOSS | 两段真实伤害 |

这四个连招的组成方式完全一致，差异只在于子技能的个数与参数。运行输出中可以清楚看到一次 `execute()` 调用引发连续三段伤害，见 4.3.2 节。

**与观察者、状态的联动**：连招内部的每一段子技能在结算时都会照常向事件总线广播事件（观察者模式），而其中带控制效果的段落在命中后又会调用 `inflictState()`（状态模式）。因此**一次"大招"的执行会同时穿过组合、责任链、策略、状态、观察者五个模式** —— 这也是本项目"多模式协作"最有代表性的场景。

**效果与代价**：单体技能与连招在调用方眼中完全等价；新增连招只需 `ComboSkill::add()` 拼接子技能，无需修改任何调用代码；连招可以任意嵌套，形成更复杂的技能树。这也为后续扩展"技能树系统"预留了空间 —— 例如一个"终极连招"可以包含"裂地三连斩"和"冰火两重天"两个连招，代码上只需继续 `add()`。代价是容器与叶子共用同一个接口，叶子上那些"只有容器才有意义"的操作（如 `add()`）需要做出取舍；本项目采用的是"安全方式"——`add()` 只声明在 `ComboSkill` 上，`Skill` 接口不暴露它，代价是客户端在需要 `add()` 时须知道具体类型[3]。

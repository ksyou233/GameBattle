#### 2.2.3 策略模式（Strategy）

**模式意图**：定义一系列算法，把它们一个个封装起来，并且使它们可相互替换，使得算法可独立于使用它的客户而变化[1]。

**本项目面临的问题**：本系统中有**两族**独立的算法需要运行期替换，它们刚好都用策略模式解决。

**第一族是伤害计算规则。** 不同攻击方式对防御的穿透能力完全不同：物理攻击直接减去对方防御，魔法攻击只受一半防御减免，BOSS 的真实伤害则完全无视防御。如果写成条件分支：

```cpp
int damage = (type == PHYSICAL) ? atk - def
           : (type == MAGIC)    ? atk - def / 2
           :                      atk;          // 每加一种类型就要改这里
```

那么每新增一种伤害规则（毒伤、神圣伤害……）都要修改角色类，且角色类会随着规则种类增多而不断膨胀。这类"用条件判断选择算法"的写法，正是策略模式要消除的对象[1][3]。

**第二族是战斗 AI 的决策算法。** "这个单位本回合该干什么"有三种完全不同的思路：

| AI 策略 | 行为规则 | 本项目中用于 |
|---------|---------|------------|
| `AggressiveAI`（莽夫） | 不考虑防御与自身血量，从攻击技能中随机挑一个出手 | 战士、射手、暗影魔龙、哥布林战士 |
| `DefensiveAI`（保守） | 血量低于 30% 时转入防御，否则反击 | 哥布林斥候 |
| `SupportAI`（辅助） | 血量低于一半且有治疗技能时先自救，否则释放最强攻击手段 | 法师、哥布林祭司 |

**角色映射**：

| 模式角色 | 伤害策略族 | AI 策略族 |
|---------|-----------|----------|
| 抽象策略 Strategy | `DamageStrategy` | `AIStrategy` |
| 具体策略 ConcreteStrategy | `PhysicalDamage`、`MagicDamage`、`TrueDamage` | `AggressiveAI`、`DefensiveAI`、`SupportAI` |
| 上下文 Context | `Character` | `Character` |

两族策略共用同一个上下文 `Character` —— 也就是说，同一个类同时扮演两个策略模式的上下文，这本身就说明"模式"是对协作关系的命名，而不是对类的命名。

**实现要点**：上下文（`Character`）只持有抽象策略并委托调用，完全不知道背后是哪个具体算法：

```cpp
class DamageStrategy {
public:
    virtual std::string name() const = 0;
    virtual int compute(int baseAtk, int def) const = 0;   // 具体算法交给子类
};

class MagicDamage : public DamageStrategy {
public:
    std::string name() const override { return "魔法"; }
    int compute(int baseAtk, int def) const override {
        return std::max(1, baseAtk - def / 2);   // 只吃一半防御
    }
};
```

**特别值得说明的是：策略模式在本项目中不是"各自为政"，而是与其它模式产生了实际联动。** 责任链中的 `ArmorHandler` 这一个环节，内部调用的正是攻击方持有的 `DamageStrategy`：

```cpp
void ArmorHandler::handle(DamageContext& ctx) {
    int effectiveAtk = static_cast<int>(ctx.attacker->atk() * ctx.powerMultiplier);
    const DamageStrategy& strategy = ctx.attacker->damageType();   // 策略模式在此接入
    ctx.damage = strategy.compute(effectiveAtk, ctx.defender->def());
    // …把结算过程写入 trace，便于文档与答辩展示
}
```

于是**同一个结算环节**，因为攻击方持有的策略不同，就得到三套完全不同的结果：战士的巨剑会被高防御的 BOSS 大幅减伤，法师的魔法只吃一半防御，而 BOSS 的真实伤害则直线穿透。第 4.2 节给出了这一过程的真实运行轨迹。

**效果与代价**：三种伤害规则、三种 AI 行为互不影响，各自独立可测；切换算法只需换一个对象，无需修改任何调用代码。策略模式的这一特点还直接简化了单元测试 —— 每个算法都有自己的类，可以通过各自接口单独测试[3]。代价是客户端必须知道有哪些策略可选，且类的数量会随策略数量线性增加；当策略之间需要共享中间状态时，还要额外考虑上下文的职责边界。

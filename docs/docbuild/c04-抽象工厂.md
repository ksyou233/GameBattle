#### 2.2.2 抽象工厂模式（Abstract Factory）

**模式意图**：提供一个创建一系列相关或相互依赖对象的接口，而无需指定它们具体的类[1]。

**本项目面临的问题**：在游戏里，一个"职业"从来不是单个对象，而是一整套**必须配套**的产品：

| 职业 | 天赋 | 武器 | 防具 | 招牌技能 | 大招 |
|------|------|------|------|---------|------|
| 战士 | 铁壁：基础防御 +4 | 巨剑（攻击 +9） | 板甲（防御 +6） | 旋风斩（1.4 倍伤害，25% 眩晕） | 裂地三连斩（三段连招） |
| 法师 | 奥术亲和：伤害按魔法规则结算 | 秘法法杖（攻击 +7） | 法师长袍（防御 +2） | 火球术（1.6 倍伤害） | 冰火两重天（含必然冰冻） |
| 射手 | 鹰眼：基础暴击率 +10% | 穿云长弓（攻击 +6） | 皮甲（防御 +3） | 穿透射击（1.35 倍伤害） | 疾风三连射（三段连招） |

如果让调用方自己逐个 `new` 出来，会出现两个问题：一是"职业"这个概念被拆散在各处，代码里到处散落着"如果是战士就给他巨剑"这样的判断；二是**产品族的一致性无法保证** —— 稍不留神就会出现"战士拿着法杖、放着火球术"这类荒谬组合。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 抽象工厂 Abstract Factory | `HeroPackageFactory` |
| 具体工厂 Concrete Factory | `WarriorPackageFactory`、`MagePackageFactory`、`ArcherPackageFactory` |
| 抽象产品 Abstract Product | `Combatant`（武器与防具经装饰器包装后仍是它）、`Skill` |
| 具体产品 Concrete Product | 巨剑/板甲（装饰器）、旋风斩/裂地三连斩（技能）、天赋效果 |
| 客户端 Client | `main.cpp` 中的组队逻辑 |

**实现要点**：抽象工厂只声明"创建什么"，把"怎么创建"交给具体工厂[1]：

```cpp
// 抽象工厂：定义一整套产品的创建接口
class HeroPackageFactory {
public:
    virtual std::string career() const = 0;            // 职业名
    virtual std::string talent() const = 0;            // 天赋说明（给人看的文案）
    virtual void applyTalent(Character& c) const = 0;  // 产品 D：把天赋真正施加到裸角色上
    virtual std::unique_ptr<Combatant> equip(std::unique_ptr<Combatant> base) const = 0;
    virtual std::unique_ptr<Skill> signatureSkill() const = 0;   // 产品 B：招牌技能
    virtual std::unique_ptr<Skill> ultimateSkill() const = 0;    // 产品 C：大招
};
```

具体工厂的实现则体现了**与装饰器模式的协作** —— `equip()` 返回的并不是裸角色，而是已经套好武器与防具装饰器的 `Combatant`：

```cpp
std::unique_ptr<Combatant> WarriorPackageFactory::equip(std::unique_ptr<Combatant> base) const {
    base = std::make_unique<WeaponDecorator>(std::move(base), "巨剑", 9);
    base = std::make_unique<ArmorDecorator>(std::move(base), "板甲", 6);
    return base;
}
```

调用方拿到手的就是"武装形态"，完全不需要知道内部套了几层装饰器。

**天赋是第四个产品，同样由工厂产出。** 一个职业的差异不只体现在装备与技能上，还体现在基础数值和伤害规则上，因此抽象工厂里还有 `applyTalent()`：

```cpp
void WarriorPackageFactory::applyTalent(Character& c) const {
    c.addBaseDef(4);                                        // 铁壁：基础防御 +4
}

void MagePackageFactory::applyTalent(Character& c) const {
    c.setDamageStrategy(std::make_unique<MagicDamage>());   // 奥术亲和：改走魔法结算
}

void ArcherPackageFactory::applyTalent(Character& c) const {
    c.addCritRate(0.10);                                    // 鹰眼：基础暴击率 +10%
}
```

调用方按固定顺序取用工厂的产物 —— **先天赋、后装备**：

```cpp
Character* raw = body.get();                                   // 先拿到裸角色
warriorFactory.applyTalent(*raw);                              // 天赋作用于裸角色
std::unique_ptr<Combatant> unit = warriorFactory.equip(std::move(body));   // 再套装饰器
```

这个顺序并非随意：`applyTalent()` 改的是**基础属性**（`baseAtk_` / `baseDef_` / `critRate_`），而 `equip()` 套上的装饰器是在基础属性**之上**做加算（`atk() = baseAtk_ + Σ 装备加成`）。两者层次不同、互不覆盖，且都采用"累加式"接口（`addBaseDef` 而非 `setBaseDef`），因此即使调换顺序结果也相同；但按"基础 → 装饰"的顺序书写语义最清晰，也便于阅读者建立正确的心智模型。结果可以直接在运行输出里核验：亚瑟防御 = 14（基础）+ 4（铁壁）+ 6（板甲）= 24，莉娜暴击率 = 30%（基础）+ 10%（鹰眼）= 40%。

注意 `talent()` 与 `applyTalent()` 是配套的一对：前者返回给玩家看的说明文字，后者是它对应的实际效果。答辩时可以主动点出这一对的意义 —— 只打印天赋文字却不改数值，就是典型的"文档与实现脱节"；把两者放进同一个工厂，才谈得上"产品族的一致性"。本文 5.6 节记录了本组在自查中发现并修复这一问题的完整过程。

**为什么用抽象工厂而不是工厂方法**：工厂方法（Factory Method）解决的是"**一个**产品的创建延迟到子类"；抽象工厂解决的是"**一整个产品族的一致性创建**[1]"。本项目中武器、防具、技能必须成套出现，所以选用抽象工厂。这是答辩中经常被要求对比的一对模式。

**效果与代价**：新增一个职业（例如"牧师"）只需要新增一个具体工厂类，`main.cpp` 中改一行创建工厂的代码，既有代码零改动；同时由于产品族由同一个工厂产出，一致性得到了结构性保证。代价是当产品族需要**新增一个产品种类**（例如再增加一类"饰品"）时，抽象工厂基类与全部三个具体工厂都要跟着改 —— 抽象工厂擅长的是"扩展产品族"，不擅长"扩展产品种类"。

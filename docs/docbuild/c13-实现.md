## 3 实现

### 3.1 工程结构

项目采用"头文件按模块分目录、实现文件与之一一对应"的组织方式，共 13 个头文件、11 个实现文件、1 个主程序（有效代码 1556 行，注释 597 行）：

```
GameBattle/
├── include/                     头文件（按所属模块分目录）
│   ├── core/
│   │   ├── GameConfig.hpp       单例：全局配置与随机源
│   │   └── EventBus.hpp         观察者：事件类型、观察者接口、主题
│   ├── character/
│   │   ├── Combatant.hpp        参战单位抽象接口（装饰器的统一类型）
│   │   ├── Character.hpp        具体角色（状态/策略/技能表的载体）
│   │   └── HeroPackageFactory.hpp  抽象工厂：职业产品族
│   ├── skill/
│   │   └── Skill.hpp            组合模式：技能抽象、单体技能、治疗、连招
│   ├── equipment/
│   │   └── EquipmentDecorator.hpp  装饰器：装备加成与附魔
│   ├── combat/
│   │   ├── DamageStrategy.hpp   策略：物理/魔法/真实伤害
│   │   ├── AIStrategy.hpp       策略：莽夫/保守/辅助 AI
│   │   ├── DamageChain.hpp      责任链：四段伤害结算流水线
│   │   └── CharacterState.hpp   状态：正常/眩晕/冰冻/狂暴
│   ├── observer/
│   │   └── BattleObserver.hpp   观察者：日志/成就/BOSS 阶段/回放
│   └── battle/
│       └── Battle.hpp           回合制战斗主循环
├── src/                         与 include 一一对应的实现文件
├── main.cpp                     演示入口（三幕）
├── CMakeLists.txt               CMake 构建脚本
├── build.bat / build.sh         一键编译运行脚本
├── README.md                    编译运行说明
└── docs/                        设计文档、UML 源码与图片、运行输出
```

模块之间的依赖方向是严格单向的：`battle` → `observer` / `combat` / `skill` → `character` → `core`。整个工程不存在任何循环依赖，这一点可以由图 1 的主类图直接验证。

### 3.2 编译与运行

**方式一：一键脚本（推荐）**

Windows 下直接执行 `build.bat`；Git Bash / Linux / macOS 下执行 `bash build.sh`。脚本会完成编译并立即运行程序。

**方式二：CMake**

```bash
cmake -B build -S .
cmake --build build
./build/GameBattle.exe
```

**方式三：直接调用编译器**

```bash
g++ -std=c++17 -O2 -Wall -Iinclude \
    src/core/*.cpp src/character/*.cpp src/skill/*.cpp src/equipment/*.cpp \
    src/combat/*.cpp src/observer/*.cpp src/battle/*.cpp main.cpp \
    -o build/GameBattle.exe
```

**环境要求**：支持 C++17 的编译器即可，无任何第三方库依赖。本项目开发环境为 GCC 15.1.0（MinGW-w64），全部代码在 `-Wall` 下**零警告**编译通过。

需要说明的是：如果使用 **MinGW Makefiles** 生成器，工程所在路径不能包含中文，否则 `mingw32-make` 无法正确解析路径。这一点已实测确认并写入 README 的注意事项中；纯英文路径下 CMake 构建与运行均正常。

### 3.3 关键代码说明

**（1）单例的三条约束齐备才算单例**（`src/core/GameConfig.cpp`）

```cpp
GameConfig& GameConfig::instance() {
    // Meyers Singleton：函数内静态局部变量
    //   · C++11 起保证初始化线程安全
    //   · 程序结束时自动析构，不需要手动释放，也不会有内存泄漏
    static GameConfig theInstance;
    return theInstance;
}
```

配合头文件中的 `private` 构造函数与 `GameConfig(const GameConfig&) = delete;`，三者缺一不可。

**（2）装饰器的透明转发 + 装备链累积**（`src/equipment/EquipmentDecorator.cpp`）

```cpp
EquipmentDecorator::EquipmentDecorator(std::unique_ptr<Combatant> inner, std::string equipmentName)
    : inner_(std::move(inner)), equipmentName_(std::move(equipmentName)) {
    // 若被装饰对象本身就是一个装饰器，则把装备名接着往后拼，
    // 这样最外层拿到的是一整条"装备链"。
    const EquipmentDecorator* previous = dynamic_cast<const EquipmentDecorator*>(inner_.get());
    if (previous != nullptr) {
        chainLabel_ = previous->chainLabel_ + " + " + equipmentName_;
    } else {
        chainLabel_ = equipmentName_;
    }
}
```

**（3）责任链的中途截断**（`src/combat/DamageChain.cpp`）

`DodgeHandler::handle()` 在命中失败时直接 `return`，不调用基类的 `handle()`，链条因此终止。这是责任链模式最典型的用法；与之相对，`BlockHandler` 在折减伤害后仍然继续向后传递，见 2.2.7 节。

**（4）组合模式的递归调用**（`src/skill/Skill.cpp`）

`ComboSkill::execute()` 遍历子技能并逐个调用 `execute()`，无需区分子技能是单体还是连招，也无需自己处理递归 —— 递归由多态自然完成。

**（5）状态内部的规则**（`src/character/Character.cpp`）

`tickState()` 中，从眩晕/冰冻恢复时设置 `controlImmunityTurns_ = 1`。这条规则写在上下文的状态计时逻辑里，因为它属于"状态退出时的行为"。

**（6）观察者的重入保护**（`src/observer/BattleObserver.cpp`）

`BossPhaseObserver::onEvent()` 在调用 `inflictState()` **之前**先置位 `triggered_`，因为 `inflictState()` 会广播 `StateChanged` 事件并回调回来，不先置位会造成重复触发。

**（7）判定与广播分离**（`src/combat/DamageChain.cpp`）

链的出口 `performAttack()` 是唯一调用 `bus.notify()` 的地方。它在扣血**之后**、发伤害事件**之前**，先判断 `ctx.blocked` 并额外广播一条 `EventType::Blocked`，因此日志里格挡会以"⊘ 原因行 + 伤害结果行"两行的形式出现。

### 3.4 代码注释规范

全部源文件遵循统一的注释规范：

1. **文件头注释**：每个头文件顶部都有一段块注释，说明本文件承担哪个设计模式、意图是什么、在本项目中的落点是什么、为什么这样设计。这是本项目注释的重点 —— 让任何一位读者打开任意一个头文件，都能立刻明白它存在的理由。
2. **接口注释**：所有公开接口都有 `///` 文档注释，说明参数含义、返回值与副作用（例如"返回实际扣减的血量（可能因状态易伤而被放大）"）。
3. **关键逻辑行内注释**：所有"看起来可以省略但实际省略会出错"的地方都有行内注释。例如"先置位，避免状态变化事件回调进来再次触发""格挡不 return：仍须向后传递"等。
4. **反面示例注释**：在 2.2 节的文档中，我们用"反面写法（本项目未采用）"的形式对比了硬编码实现与模式化实现的差异，说明选择某个模式的动机。良好的注释应当解释"为什么"，而不是复述"是什么"[7]。

全工程共 597 行注释，占有效代码行数（1556 行）的 38%，且注释内容均为对设计意图与工程细节的说明，而非对代码字面意思的重复。

### 3.5 可复现性与静态检查

"可运行代码"不能只靠口头声明。本组在交付前对工程做了三项独立验证，全部结果如下：

| 验证项 | 做法 | 结果 |
|-------|------|------|
| 严格编译 | `g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -Wshadow -Iinclude`（24 个头文件 + 全部 .cpp + `main.cpp`） | 退出码 0，**零警告、零错误** |
| 调试构建复跑 | `-O0 -g -D_GLIBCXX_DEBUG -D_GLIBCXX_ASSERTIONS` 编译并运行 | 退出码 0，标准库断言全部通过，输出与 `-O2` 版本**逐字节一致** |
| 输出可复现 | 对同一份输出取 md5 并与仓库中的 `docs/演示输出.txt` 比对 | md5 一致，均为 168 行 / 10714 字节 |

三项验证的具体含义是：

1. **严格编译**：在 `-Wall -Wextra -Wpedantic -Wshadow` 全开的条件下，工程没有任何一条警告。其中 `-Wshadow` 专门用于检查变量遮蔽，`-Wpedantic` 用于检查非标准扩展 —— 两者同时为零，说明代码没有依赖任何编译器特有的行为。
2. **调试构建复跑**：`-D_GLIBCXX_DEBUG` 会启用 libstdc++ 的检查版容器与迭代器，任何越界访问、失效迭代器使用、`std::sort` 的比较器不满足严格弱序等问题都会在运行期直接报错。本工程在该模式下运行到结束且输出不变，说明没有此类问题。
3. **输出可复现**：由于随机种子固定为 `20261010` 且随机源唯一（单例模式保证），同一份代码在任何符合 C++17 的编译器上运行，输出应当逐字节一致。这一条把本文第 4 章的全部数字变成了"可复查"的 —— 阅卷者只需按 3.2 节编译运行一次，即可用 `diff` 命令核对本文引用的每一行输出。

**一处需要如实说明的限制**：本组使用的 MinGW-w64 工具链（GCC 15.1.0）**不提供** `-fsanitize=address` 与 `-fsanitize=undefined` 所需的运行库（链接时会报 `cannot find -lubsan`），因此无法在本机进行地址与未定义行为的动态检测。为尽量弥补，本项目全程使用 `std::unique_ptr` 管理所有权，没有出现任何裸 `new`/`delete`；启用 `-D_GLIBCXX_DEBUG` 的调试构建也在一定程度上覆盖了容器与迭代器的越界问题。上述限制不影响工程的编译与运行，特此说明。

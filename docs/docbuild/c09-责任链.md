#### 2.2.7 责任链模式（Chain of Responsibility）

**模式意图**：使多个对象都有机会处理请求，从而避免请求的发送者与接收者之间的耦合。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止[1]。

**本项目面临的问题**：一次攻击真正造成多少伤害，并不是一个公式能算完的，而要依次经过四道判定，而且每一道都可能改变结果、甚至直接终止整个流程：

| 顺序 | 环节 | 作用 | 能否终止流程 |
|------|------|------|------------|
| 1 | 闪避判定 `DodgeHandler` | 按防守方闪避率判定是否命中 | **能**（闪避成功则伤害归零，后续环节不再执行） |
| 2 | 护甲减伤 `ArmorHandler` | 调用攻击方的伤害策略得到基础伤害 | 否 |
| 3 | 格挡判定 `BlockHandler` | 按配置概率判定格挡，触发则伤害折减至 70%，并置位 `blocked` 标志 | 否 |
| 4 | 暴击判定 `CritHandler` | 按攻击方暴击率判定暴击，触发则伤害翻倍 | 否 |

如果把这四步写成一个巨型函数，代码会变成一大段线性判断，而且**后续想插入新环节（例如"反伤"、"护盾吸收"、"减伤光环"）就必须动这个大函数**，风险很高。在游戏开发中，把一次攻击拆成若干可插拔的结算步骤是一种通行做法[5]，原因也很直接：战斗规则的调整频率远高于系统的其它部分，规则一旦被写死在函数体里，每次调平衡都要重新读一遍整个函数。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 抽象处理者 Handler | `DamageHandler` |
| 具体处理者 ConcreteHandler | `DodgeHandler`、`ArmorHandler`、`BlockHandler`、`CritHandler` |
| 客户端与链的组装者 Client | `DamageChain` |
| 请求与上下文 | `DamageContext` |

**实现要点**：抽象处理者持有一个指向下一环的指针，默认行为是"自己不处理，直接交给下一环"：

```cpp
class DamageHandler {
public:
    void setNext(DamageHandler* next) { next_ = next; }
    virtual void handle(DamageContext& ctx) {
        if (next_ != nullptr) next_->handle(ctx);   // 默认：向后传递
    }
    virtual std::string name() const = 0;
protected:
    DamageHandler* next_ = nullptr;
};
```

**中途截断**是责任链最典型的用法，在本项目中由 `DodgeHandler` 实现：

```cpp
void DodgeHandler::handle(DamageContext& ctx) {
    if (GameConfig::instance().roll01() < ctx.defender->dodgeRate()) {
        ctx.dodged = true;
        ctx.damage = 0;
        ctx.trace.push_back("闪避判定：命中失败，链条终止");
        return;                       // 关键：不再调用基类的 handle()，链条就此结束
    }
    ctx.trace.push_back("闪避判定：命中");
    DamageHandler::handle(ctx);       // 继续向后传递
}
```

注意第 3 环 `BlockHandler` 与第 1 环的差别：**格挡不截断流程**，它在把伤害折减到 70% 之后仍然调用 `DamageHandler::handle(ctx)` 继续向后传递，只是多置了一个 `blocked` 标志位。如果照抄"一处理完就 return"的写法，暴击环节就永远不会执行，伤害会凭空少一半 —— 这是责任链在使用中最容易踩的坑："处理"不等于"终止"。

**与策略模式的交叉**：第 2 环 `ArmorHandler` 内部调用的正是攻击方持有的 `DamageStrategy`，因此这一环既体现了责任链的"逐级加工"，又体现了策略模式的"算法可替换"：

```cpp
void ArmorHandler::handle(DamageContext& ctx) {
    int effectiveAtk = static_cast<int>(ctx.attacker->atk() * ctx.powerMultiplier);
    const DamageStrategy& strategy = ctx.attacker->damageType();   // 策略模式在此接入
    ctx.damage = strategy.compute(effectiveAtk, ctx.defender->def());
    DamageHandler::handle(ctx);
}
```

**一次攻击的完整伤害公式（五步）**：需要特别澄清的是，责任链只覆盖了其中的第 1 至第 4 步，第 5 步在链**之外**：

```
0. atk() = lround(baseAtk × state.atkMultiplier())      ← 状态模式：攻击力受当前状态影响
   def() = lround(baseDef × state.defMultiplier())      ← 状态模式：防御力受当前状态影响
1. 闪避  roll01() < defender.dodgeRate() → 伤害置 0，链条终止
2. 护甲  strategy.compute((int)(atk × power), defender.def())   ← 策略模式在此接入
3. 格挡  roll01() < 0.18 → (int)(dmg × 0.70)，只置位 ctx.blocked，不截断
4. 暴击  roll01() < attacker.critRate() → (int)(dmg × 2.0)
5. 易伤  real = lround(dmg × state.incomingMultiplier())   ← 【在责任链之外】
```

第 5 步位于 `Character::takeDamage()` 内部，由状态模式负责。**因此"日志显示的数字"并不等于"责任链算出的数字"**：责任链的产出是第 4 步的结果，而日志打印的是第 5 步之后的实际扣血量。理解这一点，才能正确复算 4.3.4 节中的每一个数字。

注意第 3 步与第 4 步的**先后顺序**也很关键：两者虽然都是乘法，但 `(int)` 截断的位置不同，先格挡后暴击与先暴击后格挡在个别数值上会出现 1 至 2 点的差异。本项目采用的是"先格挡、后暴击"。

**上下文设计的一个额外收获**：`DamageContext` 中有一个 `trace` 字段，每个环节都把自己的判定结果追加进去。这本来只是为了调试，但最终成为了一份极具说服力的材料 —— 每一刀都能输出完整的结算轨迹，"这一次伤害到底是怎么算出来的"有了直接证据。第 4.2 节展示的就是程序真实输出的轨迹。

**链的组装**：四个环节在 `DamageChain` 的构造函数中按固定顺序串联，想新增环节（例如"护盾吸收"）只需在这里插一行：

```cpp
DamageChain::DamageChain() {
    handlers_.push_back(std::make_unique<DodgeHandler>());
    handlers_.push_back(std::make_unique<ArmorHandler>());
    handlers_.push_back(std::make_unique<BlockHandler>());
    handlers_.push_back(std::make_unique<CritHandler>());
    for (std::size_t i = 0; i + 1 < handlers_.size(); ++i) {
        handlers_[i]->setNext(handlers_[i + 1].get());
    }
}
```

**环节只负责判定，广播集中在出口**：四个环节都不直接调用 `notify()`，它们只把结论写进 `DamageContext`（`dodged` / `blocked` / `crit` / `damage`）。真正对外广播事件的是链的出口 `performAttack()` —— 它先看 `ctx.dodged` 决定是否发 `Dodged`，扣血后再按 `ctx.crit` 发 `CriticalHit` 或 `DamageDealt`，并在 `ctx.blocked` 为真时额外发一条 `Blocked`。这样安排的好处是：**每个环节只对"判定"负责，事件类型与广播时机集中在一处**，既避免了四个环节各自向总线发事件的混乱，也让责任链与观察者两个模式的分工变得清晰。想新增一种结算结果，只需在 `DamageContext` 里加一个标志位、在出口加一个分支，四个环节本身一行都不用改。

**效果与代价**：四个判定环节各自独立、可单独测试与调整顺序；新增结算环节的改动被限制在"新增一个类 + 在链上插一行"。代价是请求不保证一定被处理（本项目通过在最末端环节兜底处理来规避），且当链较长时，调试一次请求究竟在哪一环被改变需要依赖 `trace` 之类的可观测手段。

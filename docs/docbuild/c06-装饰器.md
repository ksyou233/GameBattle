#### 2.2.4 装饰器模式（Decorator）

**模式意图**：动态地给一个对象添加一些额外的职责。就增加功能而言，装饰器比生成子类更为灵活[1]。

**本项目面临的问题**：装备系统的组合爆炸问题。假设有四类可叠加的加成 —— 武器、防具、附魔、宝石 —— 如果靠继承实现，就需要为每一种组合派生一个类：

```
战士、战士+巨剑、战士+巨剑+板甲、战士+巨剑+板甲+烈焰附魔、战士+巨剑+板甲+烈焰附魔+暴击宝石……
```

4 类加成就是 2⁴ = 16 个子类，而且**顺序也无法在运行期调整**（"先附魔后镶宝石"和"先镶宝石后附魔"如果效果应该相同，靠继承就要再写一遍）。更麻烦的是，一旦新增第 5 类加成，子类数量直接翻倍。这正是经典文献中所指出的"用继承扩展功能会导致类数量指数增长"的典型症状[1][15]。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 抽象构件 Component | `Combatant` 接口 |
| 具体构件 ConcreteComponent | `Character`（裸角色） |
| 装饰器基类 Decorator | `EquipmentDecorator` |
| 具体装饰器 ConcreteDecorator | `WeaponDecorator`、`ArmorDecorator`、`FireEnchantDecorator`、`CritGemDecorator` |
| 客户端 Client | `HeroPackageFactory::equip()`、`main.cpp` 第一幕演示 |

**实现要点**：装饰器能够"套娃"的关键，在于**它自身也实现了被装饰对象的同一接口**[1]：

```cpp
class EquipmentDecorator : public Combatant {      // 与 Character 实现同一个接口
public:
    EquipmentDecorator(std::unique_ptr<Combatant> inner, std::string equipmentName);

    // 属性：在被装饰对象的基础上叠加自己的加成
    int atk() const override { return inner_->atk() + bonusAtk(); }
    int def() const override { return inner_->def() + bonusDef(); }
    double critRate() const override { return inner_->critRate() + bonusCrit(); }

    // 其余方法一律原样透传给 inner_
    int takeDamage(int amount, const std::string& source) override {
        return inner_->takeDamage(amount, source);
    }
    // …………
protected:
    virtual int bonusAtk()  const { return 0; }    // 三个加成钩子，子类只覆写关心的那个
    virtual int bonusDef()  const { return 0; }
    virtual double bonusCrit() const { return 0.0; }
private:
    std::unique_ptr<Combatant> inner_;             // 被装饰对象（也可能是另一个装饰器）
};
```

子类只需要覆写自己关心的那一个钩子方法，其余全部继承：

```cpp
class FireEnchantDecorator : public EquipmentDecorator {
protected:
    int bonusAtk() const override { return 7; }
    // 覆写 damageType()，把整条伤害结算路径切换为魔法规则
    const DamageStrategy& damageType() const override { return fireStrategy_; }
private:
    MagicDamage fireStrategy_;
};
```

这里使用"钩子方法"而不是让每个子类自己覆写 `atk()`/`def()`/`critRate()`，是为了把"叠加"这一共同逻辑收敛到基类一处。若让子类各自覆写，则"忘记调用 `inner_->atk()`"这类错误无法被编译器发现。

**一个容易被忽略的工程细节**：装饰器的 `describe()` 方法刻意**没有**调用 `inner_->describe()`。因为如果那样写，打印出来的会是被装饰对象的"裸属性"（`Character::describe()` 打印的是未叠加装备的基础值），造成"装备明明加上了、面板却没变"的错觉。因此装饰器坚持以自己对外暴露的属性（即已叠加加成后的值）来描述自身，并通过在构造时用 `dynamic_cast` 判断 `inner_` 是否也是装饰器，把装备名累积成一条完整的装备链 —— 运行结果中打印的"巨剑 + 烈焰附魔 + 暴击宝石"就是这么来的。

**与策略模式的联动（本项目的亮点之一）**：`FireEnchantDecorator` 只覆写了一个 `damageType()` 方法，就换掉了整条伤害结算流水线的算法。程序运行结果清楚地印证了这一点：

```
② 装上巨剑后：    ATK 39  DEF 10  暴击率 15%  伤害类型：物理  | 装备：巨剑
③ 附加烈焰附魔后：ATK 46  DEF 10  暴击率 15%  伤害类型：魔法  | 装备：巨剑 + 烈焰附魔
④ 镶嵌暴击宝石后：ATK 46  DEF 10  暴击率 27%  伤害类型：魔法  | 装备：巨剑 + 烈焰附魔 + 暴击宝石
```

从②到③，攻击力 +7 只是表面现象，实质是**伤害类型从物理变成了魔法**——这意味着这次攻击在责任链的护甲环节会用一套完全不同的规则结算。装饰器负责"加职责"，策略负责"换算法"，装饰器顺手把策略也换掉，两个模式在此天然互补。

**效果与代价**：装备的叠加不再需要 2ⁿ 个子类，只需 4 个薄薄的装饰器；运行期可以任意层数、任意顺序地包裹；新增第 5 类加成只需再写一个类（约 5 行代码）。代价是装饰器链上的对象数量会增多，调试时"某一层到底加了多少"不再一眼可见，需要用 `describe()` 之类的自省手段把链路打印出来（本项目正是这么做的）。

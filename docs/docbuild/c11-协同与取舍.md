#### 2.2.9 类关系的汇总与说明

上文按模式逐一介绍了各类的职责，本节从"关系类型"的角度做一次横向汇总。图 1 中一共出现 **45 个类型**（2 个接口、7 个抽象类、35 个具体类、1 个枚举），它们之间共有 **54 条关系边**，按 UML 的关系种类统计如下：

| 关系类型 | 条数 | 语义 | 代表性实例 |
|---------|------|------|-----------|
| 实现 Realization | 6 | 类实现接口，必须提供全部纯虚函数 | `Character` ⇢ `Combatant`；`EquipmentDecorator` ⇢ `Combatant`；4 个观察者 ⇢ `IBattleObserver` |
| 泛化 Generalization | 24 | 子类继承抽象基类（分属 7 个抽象基类） | `Skill` ← `AttackSkill`/`HealSkill`/`ComboSkill`；`DamageHandler` ← `Dodge`/`Armor`/`Block`/`Crit` |
| 聚合 Aggregation | 7 | 整体与部分，部分可独立存在 | `Battle` ◇→ `Combatant`；`EventBus` ◇→ `IBattleObserver`；`ComboSkill` ◇→ `Skill`；`DamageChain` ◇→ `DamageHandler` |
| 关联 Association | 4 | 长期持有的引用关系 | `Character` → `DamageStrategy` / `AIStrategy` / `CharacterState`；`BossPhaseObserver` → `Combatant` |
| 依赖 Dependency | 13 | 仅在方法内临时使用 | `DamageChain` ⇢ `GameConfig`；`ArmorHandler` ⇢ `DamageStrategy`；`Battle` ⇢ `BattleResult` |

三点值得特别说明：

1. **抽象与实现分离得比较彻底。** 45 个类型里有 9 个是抽象类型（接口或抽象类），全部 30 条"实现 + 泛化"关系都指向这 9 个抽象类型，没有任何一条泛化关系指向具体类。这意味着**继承体系只用于"接口—实现"这一种目的**，没有出现"为了复用代码而继承实现"的情况[15]。
2. **装饰器能"套娃"的根本原因是实现关系。** `Character` 与 `EquipmentDecorator` 同时实现 `Combatant`（见上表第一行的两条），因此装饰器可以持有任意 `Combatant` —— 包括另一个装饰器。如果 `EquipmentDecorator` 选择继承 `Character`，那么它就只能包装 `Character`，整个装饰体系将无法成立。
3. **聚合关系集中在四处，且方向单一。** 7 条聚合里有 6 条是"上层持有下层"（`Battle`、`EventBus`、`DamageChain`、`ComboSkill`、`EquipmentDecorator`），只有 `Character` ◇→ `Skill` 是由上下文持有算法族。所有聚合都没有反向边，这正是 2.1.3 节"三层单向依赖"在关系层面的体现。

### 2.3 模式的协同与设计取舍

#### 2.3.1 四处关键协同

本项目的 8 个模式不是 8 个孤立的小例子，而是在同一个系统里互相咬合。以下四处协同最能说明问题。

**协同一：装饰器 ⇄ 策略 —— 一次附魔，整套伤害算法被换掉。**

`FireEnchantDecorator` 只覆写了一个 `damageType()` 方法。由于责任链的护甲环节是通过 `attacker->damageType()` 取得算法的，所以这一层装饰同时改变了两件事：面板上的攻击力，以及整条结算路径的计算规则。这是"装饰器负责加职责、策略负责换算法"两者互补的直观体现（证据见 4.1 节：第 ③ 行的伤害类型由物理变为魔法）。

**协同二：观察者 ⇄ 状态 —— BOSS 二阶段。**

战斗结算完全不知道 BOSS 有第二阶段，它只广播"掉血了"。`BossPhaseObserver` 监听到血量跌破阈值后调用 `inflictState(Berserk)`，控制权交给状态模式的 `switchState()`。三个模式（观察者、状态、以及承担广播职责的战斗循环）通过事件总线松耦合地拼在一起，整条功能的接入成本是**一行 `attach()`**（证据见 4.3.3 节）。

**协同三：责任链 ⇄ 策略 ⇄ 单例 —— 一条流水线里的三个模式。**

在 `ArmorHandler` 这一个环节内部，同时用到了策略模式（取攻击方的伤害算法）和单例模式（暴击环节取全局的暴击倍率与随机数）。这说明设计模式并不是"一个模块一个模式"的对应关系，而是可以在同一条代码路径上分层叠加的。

**协同四：责任链 ⇄ 观察者 —— "判定"与"广播"分离。**

责任链的四个环节都不直接广播事件，只把结论写进 `DamageContext`；真正广播的是链的出口 `performAttack()`。以格挡为例：第 3 环 `BlockHandler` 只置一个 `blocked` 标志，出口据此额外发一条 `EventType::Blocked`，随后被战斗日志（`⊘` 前缀）与成就系统（「铜墙铁壁」）两个观察者分别消费。把"算"与"喊"分开，环节不必关心有谁在听，出口也不必关心有几种结果 —— 想再加一种结算结果，只需在上下文里加一个标志位、在出口加一个分支，四个环节一行都不用改。

#### 2.3.2 设计取舍说明

设计过程中我们做过若干取舍，这些取舍本身就是对模式理解深度的体现，故一并记录如下。

| 问题 | 我们的选择与理由 |
|------|----------------|
| 为什么 `Combatant` 接口定义得比较宽（把技能表、AI 策略、状态都提升到接口层）？ | 为了让装饰器可以**完全透明地转发**这些能力。否则战斗循环拿到的是被装饰后的 `Combatant`，需要 `dynamic_cast` 向下转型才能取到技能表和 AI。用略宽的接口换取调用方**全程零向下转型**，是刻意的取舍。 |
| 为什么状态类只提供"系数"而不直接操作角色？ | 避免状态类反向依赖 `Character` 造成循环引用，同时保留了状态模式最核心的价值 —— 消除状态判断的 `if-else` 树。 |
| 为什么控制抗性规则要放在状态里？ | 因为它属于"状态退出时的行为"，而不是某个技能的职责。放进状态类后，所有技能都自动获得这个规则，无需各自实现一遍。 |
| 为什么 `BerserkState` 免疫控制？ | 否则玩家一个控制技能就能把 BOSS 的爆发期白白拖过去，二阶段设计形同虚设。 |
| 为什么用抽象工厂而不是工厂方法？ | 工厂方法解决"一个产品的创建延迟到子类"，抽象工厂解决"一整个产品族的一致性创建"。本项目天赋、武器、防具、技能必须配套，所以用抽象工厂。 |
| 为什么天赋也要由工厂产出（`applyTalent()`）？ | 因为"职业"的差异不止体现在装备与技能上，还体现在基础数值与伤害规则上。只打印一句天赋说明却不改数值，就是"说明与实现脱节"。把 `talent()`（文案）与 `applyTalent()`（效果）放进同一个工厂，产品族的一致性才是完整的。 |
| 为什么装饰器的 `describe()` 不调用 `inner_->describe()`？ | 否则打印出的会是被装饰对象的"裸属性"，造成"装备加上了但面板没变"的错觉。装饰器应以自己对外暴露（已叠加）的属性为准。 |
| 为什么格挡环节不 return，而暴击环节在链末？ | 格挡只是"折减伤害"，请求仍须向后传递；若在格挡处 return，暴击判定将永远不执行。这是责任链中"处理"与"终止"必须分清的地方。 |
| 为什么事件对象的 `trace` 字段要保留在正式代码里？ | 它把"一次伤害是怎么算出来的"变成了可展示的证据，既方便调试，也直接成为文档与答辩的材料。 |
| 为什么没有为"战斗日志格式化"引入建造者模式？ | 那段逻辑只有十几行、且没有任何变化点。模式只在存在变化点时才带来收益，此处引入反而会增加三个类。 |

#### 2.3.3 可扩展性验证

设计模式的最终检验标准是"改动成本"[6]。下表列出若干常见需求在**当前架构**下的改动量，用以说明模式确实带来了可扩展性：

| 想新增的功能 | 需要做什么 | 需要改动的既有代码 |
|-------------|-----------|------------------|
| 新增职业"牧师" | 新增一个具体工厂类 | **0 行** |
| 给某职业换一套天赋 | 覆写该工厂的 `applyTalent()` | **0 行** |
| 新增伤害类型"毒伤" | 新增一个 `DamageStrategy` 子类 | **0 行** |
| 新增"护盾吸收"结算环节 | 新增一个 `DamageHandler` 并插到链上 | **1 行**（链的构造函数） |
| 新增"伤害统计面板" | 新增一个 `IBattleObserver` 实现 | **1 行**（`bus.attach`） |
| 新增状态"中毒" | 新增一个 `CharacterState` 子类 | **1 行**（`makeState`） |
| 技能树中再嵌一层连招 | 直接用 `ComboSkill::add()` 嵌套 | **0 行** |
| 新增第 5 类装备加成（戒指） | 新增一个 `EquipmentDecorator` 子类 | **0 行** |

这八项改动中，**六项为 0 行、两项为 1 行**，且那两处"1 行"都位于明确的装配点（链的构造函数与 `attach` 调用处），不涉及任何业务逻辑。这就是"高内聚低耦合"可以被量化后的样子。

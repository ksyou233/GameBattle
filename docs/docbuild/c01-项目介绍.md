## 1 项目介绍

### 1.1 项目背景与选题动机

设计模式是对"在特定场景下反复出现的设计问题"所给出的可复用解法，它不是语法特性，也不是库函数，而是一套被反复验证过的经验词汇[1]。正因如此，**设计模式的价值只有在"存在真实变化点"的系统里才能体现**。课程中我们逐个学习了二十余种模式，但把每一种单独写成一个孤立的小例子，很难回答一个关键问题：**当同一个系统同时面对多个变化维度时，模式之间是怎么协作的？** 而在真实的软件工程实践中，恰恰是这种"多模式共存"的形态更为常见；有研究早已指出，模块划分的依据应当是信息隐藏与变化隔离，而不是处理流程的先后次序[14]。

我们选择"游戏战斗与技能系统"作为载体，因为它在很小的代码体量内天然包含了多个正交的变化维度：

| 变化维度 | 在本项目中的具体表现 | 如果硬编码实现会怎样 |
|---------|--------------------|-------------------|
| 参战单位的产生 | 战士、法师、射手各有配套的武器、防具与技能 | 职业概念散落各处，新增职业需要改动多个位置 |
| 伤害的计算规则 | 物理伤害直接减防御、魔法伤害只吃一半防御、真实伤害无视防御 | 各处的条件分支不断膨胀，每加一种规则就要改动角色类 |
| 装备的组合方式 | 武器、防具、附魔、宝石可自由叠加，顺序也可调整 | 靠继承实现时组合数随加成类别数呈 2ⁿ 增长 |
| 角色的临时状态 | 正常、眩晕、冰冻、狂暴会改变行动能力与攻防系数 | 角色类被大量状态判断淹没，可读性急剧下降 |
| 战斗中的旁支功能 | 日志、成就统计、BOSS 阶段切换、战斗回放 | 战斗结算逻辑被与战斗无关的功能污染 |
| 技能的组织方式 | 单体技能与多段连招需要被一致地调用 | 调用方必须区分两者并递归展开，破坏调用一致性 |

一个系统里同时出现这六个变化维度，正是设计模式最能发挥作用的场景。本文采用的 8 个模式分别对应其中的一到两个维度，并且**彼此之间存在真实的协作关系**（详见 2.3 节）。

需要说明的是，本文的取舍原则是"**有变化点才用模式**"，而不是"模式用得越多越好"。凡是没有变化维度的地方（例如战斗日志的格式化、生命值与攻击力的存取），本文都直接使用普通成员函数实现，刻意不引入任何模式 —— 这一点在 5.1 节还有进一步说明。

### 1.2 项目功能概述

系统实现了一套完整的回合制战斗流程，主要功能如下：

1. **角色构建**：通过职业包工厂一次性装配出"天赋 + 武器 + 防具 + 招牌技能 + 大招"配套完整的英雄；怪物则直接构造。
2. **技能系统**：既有单段攻击技能（旋风斩、火球术、穿透射击）、治疗技能，也有多段连招（裂地三连斩、冰火两重天、疾风三连射、暗影吐息）。连招内部可以继续嵌套连招，构成技能树。
3. **装备与附魔**：武器、防具、烈焰附魔、暴击宝石可以任意层数与顺序地包裹到角色身上，每一层都会实时改变角色的面板属性；烈焰附魔还会把整条伤害结算路径切换为魔法规则。
4. **战斗结算**：一次攻击要经过"闪避判定 → 护甲减伤 → 格挡判定 → 暴击判定"四道关卡，每一步都会改变结果甚至中途终止流程。
5. **状态机**：角色可以处于正常、眩晕、冰冻、狂暴四种状态，不同状态下行动能力与攻防系数不同；狂暴状态免疫控制，从控制中恢复的单位有短暂控制抗性。
6. **事件广播**：战斗过程中的每一次掉血、暴击、治疗、状态变化、阵亡都会以事件的形式广播，由日志、成就、BOSS 阶段监听、战斗回放四个互不相识的模块分别消费。
7. **AI 决策**：每个单位都持有一个可替换的 AI 策略，实现了莽夫、保守、辅助三种行为风格。

上述功能全部可以通过一次编译、一次运行完整演示：程序在控制台依次输出三幕（装饰器动态武装 → 责任链结算轨迹 → 一整场完整战斗），无需任何交互输入，也不依赖任何外部数据文件。

### 1.3 运行环境与技术选型

| 项目 | 说明 |
|------|------|
| 开发语言 | C++17 |
| 编译环境 | GCC 15.1.0（MinGW-w64），另提供 CMake 构建脚本 |
| 第三方依赖 | **无**。全部使用标准库，便于在任何环境复现 |
| 运行方式 | 控制台程序，运行后依次输出三幕演示，无需任何交互输入 |
| 代码规模 | 13 个头文件、11 个实现文件、1 个主程序；有效代码 1556 行，注释 597 行，含空行共 2593 行（由 `docs/docbuild/_stat.py` 实测统计） |
| 随机性 | 由全局单例统一提供随机源，`main()` 中固定种子 `20261010` |

选择 C++ 而非 Java 的原因有三：其一，C++ 的 `unique_ptr` 能直观地表达"装饰器链"与"组合树"的所有权关系，所有权语义与结构语义完全一致[8]；其二，C++ 的纯虚函数与多重实现让接口与实现的分离更显式；其三，本项目全程不依赖第三方库，交付后任何一台装有 C++17 编译器的机器都能直接复现。C++17 标准中"函数内静态局部变量的初始化是线程安全的"这一保证[9]，也正是本项目单例实现方式（见 2.2.1 节）成立的前提。

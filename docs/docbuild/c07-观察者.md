#### 2.2.5 观察者模式（Observer）

**模式意图**：定义对象间的一对多依赖，当一个对象（主题）状态改变时，所有依赖它的对象（观察者）都得到通知并自动更新[1]。

**本项目面临的问题**：战斗过程中会产生大量"值得被记录或响应"的事情 —— 掉血、暴击、闪避、格挡、治疗、状态变化、单位阵亡。而这些事情有多类互不相关的消费者：

- 战斗日志：需要把事件格式化成人类可读的一行文字；
- 成就系统：需要跨回合累计暴击次数、格挡次数与击杀数，达到阈值时解锁成就；
- BOSS 阶段监听：需要在 BOSS 血量跌破 50% 时触发二阶段狂暴；
- 战斗回放：需要把全部事件按时间顺序录下来，战斗结束后导出战报。

如果让伤害结算代码直接依次调用这四个模块，会带来两个恶果：一是**战斗结算被严重污染**，一个本该只负责"算伤害"的方法里塞满了打印日志、统计成就的代码；二是**每新增一个功能都要修改结算代码**，违反开闭原则[15]。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 抽象主题 Subject | `EventBus` |
| 抽象观察者 Observer | `IBattleObserver` |
| 具体观察者 ConcreteObserver | `BattleLogObserver`、`AchievementObserver`、`BossPhaseObserver`、`BattleRecorderObserver` |
| 事件数据 | `BattleEvent` |
| 事件源 | `Battle`（回合与生死事件）、`Character`（状态变化事件） |

**实现要点**：主题侧只维护一份订阅名单，广播时逐个通知，完全不关心观察者是谁、有几个：

```cpp
void EventBus::notify(const BattleEvent& event) {
    // 遍历订阅者名单逐个推送。
    // 这里故意不关心观察者是谁、有几个 —— 这正是观察者模式"解耦"的体现。
    for (IBattleObserver* observer : observers_) {
        if (observer != nullptr) {
            observer->onEvent(event);
        }
    }
}
```

观察者侧只依赖 `BattleEvent` 这一份数据结构：

```cpp
class IBattleObserver {
public:
    virtual ~IBattleObserver() = default;
    virtual void onEvent(const BattleEvent& event) = 0;   // 收到事件后的回调
    virtual std::string observerName() const = 0;
};
```

注意事件对象承载的是"**发生了什么**"（类型、来源、目标、数值、文案），而不是"**要怎么做**"。把决策留给观察者，主题才能保持中立 —— 这是本项目"结算只负责结算、广播只负责广播"原则在数据结构上的体现。

**本项目中最能体现观察者模式价值的功能是 BOSS 二阶段。** 战斗结算代码**完全不知道** BOSS 有第二阶段 —— 它只负责广播一条"暗影魔龙掉血了"的事件。真正决定"血量跌破 50% 就进入狂暴"的是 `BossPhaseObserver`：

```cpp
void BossPhaseObserver::onEvent(const BattleEvent& event) {
    if (triggered_ || watched_ == nullptr) return;
    // 只关心"被打"这件事，且必须打在被观察单位身上
    if (event.type != EventType::DamageDealt && event.type != EventType::CriticalHit) return;
    if (event.target != watched_->name()) return;

    double ratio = static_cast<double>(watched_->hp()) / watched_->maxHp();
    if (ratio < hpThreshold_) {
        triggered_ = true;                    // 先置位，避免状态变化事件回调进来再次触发
        watched_->inflictState(triggerState_); // 与状态模式联动：给它换个状态
    }
}
```

**新增这一整条功能的代价只有一行代码**：

```cpp
BossPhaseObserver bossPhase(boss, 0.5, StateKind::Berserk);
bus.attach(&bossPhase);     // 就这一行
```

战斗循环、伤害结算、技能系统全部零改动。这就是观察者模式"对扩展开放、对修改关闭"的直接体现。

**一个实现细节**：`triggered_` 标志必须在调用 `inflictState()` **之前**置位。因为 `inflictState()` 内部会广播 `StateChanged` 事件，而这条事件又会回调到 `onEvent()` 里来 —— 如果不先置位，就会造成重复触发甚至递归。这类"观察者回调引发的重入问题"是观察者模式在实践中必须处理好的细节，也是它"代价"的一面：主题与观察者之间的调用关系在运行时才确定，分析链路的难度高于普通的顺序调用[6]。

**另一处更能说明"一对多"的分工：格挡事件。** 责任链的第 3 环判定出格挡后，只在自己身上置一个 `blocked` 标志，并不负责对外通知；真正广播 `EventType::Blocked` 的是链的出口 `performAttack()`。这条事件被两个互不相干的观察者同时消费：战斗日志给它配了专属的 `⊘` 前缀，成就系统则累计次数、在第 3 次格挡时解锁「铜墙铁壁」：

```
  ⊘ [旋风斩] 暗影魔龙 格挡了 亚瑟 的攻击，伤害被折减
  ◆ 成就解锁：【铜墙铁壁】单场战斗成功格挡 3 次
```

"格挡"这件事只被广播了一次，而听众各取所需 —— 这正是观察者模式"一对多依赖"的字面含义。运行输出战斗统计行里那个"格挡次数"，就是成就系统这个观察者独立采集出来的，战斗结算代码里找不到任何计数器。

**效果与代价**：新增"伤害统计面板""战斗录像导出""连击提示"等功能，都只需再实现一个 `IBattleObserver` 并 `attach()` 一行，既有代码零改动。本项目在战斗结束时会输出由 `BattleRecorderObserver` 录制的完整事件序列，这就是"录制型观察者"的一个具体应用。代价是：广播的时序与次数不再由某个函数体独占描述，事件链路的可读性依赖于命名规范与文档（本项目通过统一的 `EventType` 枚举与 2.4.3 节的时序图来缓解）。

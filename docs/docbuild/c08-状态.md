#### 2.2.6 状态模式（State）

**模式意图**：允许一个对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类[1]。

**本项目面临的问题**：角色会处于"正常、眩晕、冰冻、狂暴"四种状态，而不同状态下它的行为在四个方面都不同：

| 状态 | 能否行动 | 攻击系数 | 防御系数 | 受伤系数 | 是否免疫控制 |
|------|---------|---------|---------|---------|------------|
| 正常 Normal | 可以 | ×1.0 | ×1.0 | ×1.0 | 否 |
| 眩晕 Stunned | **不可以** | ×1.0 | ×1.0 | ×1.0 | 否 |
| 冰冻 Frozen | **不可以** | ×1.0 | ×1.0 | **×1.5（破冰易伤）** | 否 |
| 狂暴 Berserk | 可以 | **×1.5** | **×0.5** | ×1.0 | **是** |

如果把这张表写进角色类，会得到一堆到处扩散的状态判断：

```cpp
// 反面写法（本项目未采用）
int atk() const {
    if (state == STUNNED) return base;
    else if (state == FROZEN) return base;
    else if (state == BERSERK) return base * 1.5;
    return base;
}
bool canAct() const { return state != STUNNED && state != FROZEN; }
int takeDamage(int d) { return state == FROZEN ? d * 1.5 : d; }
// …每加一种状态，上面每一个方法都要改
```

这正是状态模式要消除的"**以对象状态为条件的多分支**"代码[1]：判断次数与状态数、行为数相乘增长，而且新增状态时需要在每个分支处复查一遍。

**角色映射**：

| 模式角色 | 本项目对应 |
|---------|-----------|
| 上下文 Context | `Character` |
| 抽象状态 State | `CharacterState` |
| 具体状态 ConcreteState | `NormalState`、`StunnedState`、`FrozenState`、`BerserkState` |
| 状态创建 | `makeState(StateKind)`（一个服务于上下文切换的简单工厂） |

**实现要点**：本项目采用"**状态对象只提供系数与能力，由上下文负责应用**"的轻量写法。状态类只回答"我这个状态下各系数是多少、能不能行动"，不反向操作角色：

```cpp
class CharacterState {
public:
    virtual StateKind   kind() const = 0;
    virtual std::string name() const = 0;
    virtual bool   canAct() const { return true; }              // 能否行动
    virtual double atkMultiplier() const { return 1.0; }        // 攻击系数
    virtual double defMultiplier() const { return 1.0; }        // 防御系数
    virtual double incomingMultiplier() const { return 1.0; }   // 受伤系数
    virtual bool   immuneToControl() const { return false; }    // 是否免疫控制
    virtual int    duration() const { return INT_MAX; }         // 持续回合
};
```

上下文 `Character` 则只做三件事，代码里**没有任何状态判断的分支**：

```cpp
int Character::atk() const {
    // 状态对攻击力的影响在这里统一体现（例如狂暴 x1.5）
    return static_cast<int>(std::lround(baseAtk_ * state_->atkMultiplier()));
}

int Character::takeDamage(int amount, const std::string&) {
    // 冰冻等易伤状态在这里生效：先放大伤害，再扣血
    int real = static_cast<int>(std::lround(amount * state_->incomingMultiplier()));
    // …………
}
```

这样写还有一个好处：**状态类与角色类之间没有反向依赖，不会形成循环引用**，同时完整保留了状态模式"消除状态判断分支"这一核心价值。

需要特别指出的是，`takeDamage()` 里的这一行（受伤系数）**不在责任链上**：责任链算出的 `ctx.damage` 会作为参数传进来，再由这一行按当前状态放大或缩小，最后才真正扣血。也就是说，**日志里显示的伤害数字并不等于责任链算出的数字** —— 例如第 4 回合亚瑟对处于冰冻状态的 BOSS 打出的一击，责任链算得 40，而实际扣血是 `lround(40 × 1.5) = 60`。这一处"链外的一步"很容易被误读，本文在 4.3.4 节用真实日志做了逐环验算。

**两条写在状态内部的规则（模式深度的体现）**：

在实测过程中，我们发现了一个真实的平衡性缺陷：法师的大招"冰火两重天"带有 100% 概率的冰冻效果，由于法师每回合都可以释放它，BOSS 会被**从头冻到尾、一次都出不了手**，战斗完全失去意义。同样，如果 BOSS 的二阶段狂暴可以被一个控制技能轻易拖过去，那这个阶段的设计也就形同虚设。

针对这两个问题，我们在状态层面加了两条规则：

```cpp
// 规则一：狂暴状态免疫眩晕与冰冻
class BerserkState : public CharacterState {
    bool immuneToControl() const override { return true; }
};

// 规则二：从眩晕/冰冻中恢复后，获得一回合控制抗性，防止被无限连控锁死
void Character::tickState() {
    if (controlImmunityTurns_ > 0) --controlImmunityTurns_;
    if (stateTurnsLeft_ == INT_MAX) return;
    if (stateTurnsLeft_ > 0) --stateTurnsLeft_;
    if (stateTurnsLeft_ <= 0) {
        const StateKind old = state_->kind();
        if (old == StateKind::Stunned || old == StateKind::Frozen) {
            controlImmunityTurns_ = 1;      // 控制抗性
        }
        switchState(StateKind::Normal);
        stateTurnsLeft_ = INT_MAX;
    }
}
```

**这两条规则被刻意写在状态类内部，而不是散落成技能代码中 `if (目标 == BOSS)` 这样的硬编码判断。** 原因在于：它们本质上属于"状态自身的行为"，而不是某个技能的职责。这正是状态模式在工程上优于一堆 `if` 的地方 —— 规则跟着状态走，改规则只改一个类。这也印证了 5.2 节的观点：模式真正的回报体现在"变化发生时"的改动成本上。

**效果与代价**：新增一种状态（例如"中毒：每回合损失 5% 生命"）只需新增一个 `CharacterState` 子类并在 `makeState()` 里加一行，角色类与所有技能代码零改动。代价是类的数量增加（每种状态一个类），且当状态之间的迁移规则变复杂时，需要额外决定"迁移由谁驱动"（本项目选择了由 `Character::tickState()` 统一驱动，避免状态类之间互相引用）。

# 模式选型映射表

**项目名称**：游戏战斗与技能系统（GameBattle）
**大作业类型**：自拟项目综合实现
**实现语言**：C++17
**设计模式数量**：8 种（评分要求 ≥5 种）

---

## 一、模块 → 模式 → 动机 一览

| # | 设计模式 | 类别 | 落在哪个模块/类 | 解决的具体问题 | 不使用它会怎样 |
|---|---------|------|----------------|---------------|---------------|
| 1 | **单例 Singleton** | 创建型 | `core/GameConfig` | 暴击倍率、格挡概率、回合上限等规则参数与随机数发生器必须全局唯一 | 各处各持一份参数，出现"一处改了别处没改"的不一致；随机源互相独立导致战斗日志无法复现 |
| 2 | **抽象工厂 Abstract Factory** | 创建型 | `character/HeroPackageFactory` + 3 个具体工厂 | 一个"职业"是一整套配套产品：天赋＋武器＋防具＋招牌技＋大招，必须风格一致 | 调用方自己一个个 new，职业概念散落各处；新增职业要改多处；容易出现"战士拿法杖"这类不一致 |
| 3 | **策略 Strategy** | 行为型 | `combat/DamageStrategy`（物理/魔法/真实）、`combat/AIStrategy`（莽夫/保守/辅助） | 伤害计算规则与 AI 决策算法都需要在运行期替换 | `if (类型 == 物理) … else if (类型 == 魔法) …` 无限膨胀，每加一种就要改角色类 |
| 4 | **装饰器 Decorator** | 结构型 | `equipment/EquipmentDecorator` + 4 个具体装饰器 | 武器、防具、附魔、宝石的加成需要自由组合、自由顺序叠加 | 靠继承实现组合数是 2^n 级（长剑角色、长剑+重甲角色、长剑+重甲+附魔角色……） |
| 5 | **观察者 Observer** | 行为型 | `core/EventBus` + 4 个观察者 | 战斗结算不应关心日志打印、成就统计、BOSS 阶段切换等旁支功能 | 结算代码被 UI 与业务无关的杂事污染；每加一个功能都要动结算代码 |
| 6 | **状态 State** | 行为型 | `combat/CharacterState` + 4 个具体状态 | 角色处于正常/眩晕/冰冻/狂暴时，行动能力与攻防系数都不同 | 角色类里堆满 `if (state == 眩晕)`、`if (state == 冰冻)` 的分支，难以维护 |
| 7 | **责任链 Chain of Responsibility** | 行为型 | `combat/DamageChain` + 4 个处理者 | 一次攻击的伤害要经过闪避→护甲→格挡→暴击四道判定 | 写成一个巨型函数；后续想插入"反伤""护盾吸收"就得动大手术 |
| 8 | **组合 Composite** | 结构型 | `skill/ComboSkill` | 连招（多段技能）与单体技能应当能被一致地调用 | 战斗循环需要判断"这一招是普通技能还是连招"，并递归展开，破坏调用一致性 |

**类别分布**：创建型 2 种（单例、抽象工厂）、结构型 2 种（装饰器、组合）、行为型 4 种（策略、观察者、状态、责任链）——
覆盖课堂要求的三类模式。

## 二、每个模式的代码落点速查

| 模式 | 抽象角色 | 具体角色 | 上下文 / 客户端 |
|------|---------|---------|---------------|
| 单例 | — | `GameConfig` | `Character`、`DamageChain`、`AttackSkill` 通过 `GameConfig::instance()` 取参数 |
| 抽象工厂 | `HeroPackageFactory` | `WarriorPackageFactory`、`MagePackageFactory`、`ArcherPackageFactory` | `main.cpp` 的两幕演示 |
| 策略 | `DamageStrategy`、`AIStrategy` | `PhysicalDamage`/`MagicDamage`/`TrueDamage`；`AggressiveAI`/`DefensiveAI`/`SupportAI` | `Character`（持有并委托） |
| 装饰器 | `EquipmentDecorator` | `WeaponDecorator`、`ArmorDecorator`、`FireEnchantDecorator`、`CritGemDecorator` | `HeroPackageFactory::equip()`、`main.cpp` 第一幕 |
| 观察者 | `IBattleObserver`（观察者）、`EventBus`（主题） | `BattleLogObserver`、`AchievementObserver`、`BossPhaseObserver`、`BattleRecorderObserver` | `Battle`（事件源）、`Character`（状态事件源） |
| 状态 | `CharacterState` | `NormalState`、`StunnedState`、`FrozenState`、`BerserkState` | `Character`（上下文） |
| 责任链 | `DamageHandler` | `DodgeHandler`、`ArmorHandler`、`BlockHandler`、`CritHandler` | `DamageChain`（组装者）、`Skill`（发起者） |
| 组合 | `Skill` | `AttackSkill`、`HealSkill`（叶子）；`ComboSkill`（容器） | `Battle::actOnce()`（统一调用） |

## 三、模式之间的协作（答辩重点）

这 8 个模式不是 8 个孤立的小例子，而是在同一个系统里**互相咬合**的。四处最值得讲的联动：

### 联动 1：装饰器 ⇄ 策略 —— 一附魔，整套伤害算法被换掉

`FireEnchantDecorator` 只覆写了一个 `damageType()` 方法：

```cpp
const DamageStrategy& damageType() const override { return fireStrategy_; }  // 改为 MagicDamage
```

于是经这条装饰链打出的攻击，在 `ArmorHandler` 环节会用**魔法规则**结算。
程序实测输出印证了这一点：

```
② 装上巨剑后：   ATK 39  DEF 10  伤害类型：物理  | 装备：巨剑
③ 附加烈焰附魔后：ATK 46  DEF 10  伤害类型：魔法  | 装备：巨剑 + 烈焰附魔
```

**答辩可说**：装饰器负责"加职责"，策略负责"换算法"，装饰器把策略一起换掉，
两者天生互补。

### 联动 2：观察者 ⇄ 状态 —— BOSS 二阶段

战斗结算代码**完全不知道** BOSS 有第二阶段，它只是广播一句"暗影魔龙掉血了"。
`BossPhaseObserver` 监听到血量跌破 50% 后调用 `inflictState(StateKind::Berserk)`，
状态模式的 `switchState()` 接过控制权，把 BOSS 的攻击 ×1.5、防御 ×0.5。

**成本对比**：新增这一整条功能，只付出了一行代码 ——

```cpp
bus.attach(&bossPhase);
```

战斗循环、伤害结算、技能系统全部零改动。

### 联动 3：责任链 ⇄ 策略 ⇄ 单例 —— 一条伤害结算流水线里的三个模式

`ArmorHandler` 这一环内部调用了攻击方持有的 `DamageStrategy`（策略模式），
而暴击倍率来自 `GameConfig::instance()`（单例模式）。
三者叠加后，一次攻击的真实结算轨迹（程序第二幕的实际输出，逐字摘录）是：

```
1. 闪避判定：命中
2. 护甲减伤：按【物理】规则结算 60 vs DEF 30 -> 30
3. 格挡判定：未触发
4. 暴击判定：触发暴击 x2 -> 60
```

这段轨迹由 `DamageContext::trace` 在结算过程中逐环节写入，不是手工构造的示例 ——
每个处理者都把自己的判定结果追加进去，最终形成一份完整的"伤害溯源"。

### 联动 4：责任链 ⇄ 观察者 —— 格挡有自己的一条事件通道

责任链的四个环节**都不直接广播事件**，它们只把结论写进 `DamageContext`。真正广播的
是链的出口 `performAttack()`：它在 `ctx.blocked` 为真时，额外发一条 `EventType::Blocked`。
这条事件随后被两个互不相干的观察者同时消费 —— 战斗日志给它配了专属的 `⊘` 前缀，
成就系统累计次数并在第 3 次时解锁「铜墙铁壁」：

```
  ⊘ [旋风斩] 暗影魔龙 格挡了 亚瑟 的攻击，伤害被折减
  ◆ 成就解锁：【铜墙铁壁】单场战斗成功格挡 3 次
```

**答辩可说**：把"判定"与"广播"分开，是责任链与观察者协作的干净做法 ——
环节只管算，出口只管喊，听众各取所需。想再加一种结算结果（比如"反伤"），
只需在上下文里加一个标志位、在出口加一个分支，四个环节一行都不用动。

## 四、设计取舍说明（答辩可能被追问的点）

| 问题 | 我们的选择与理由 |
|------|----------------|
| 为什么 `Combatant` 接口这么宽（把技能表、AI、状态都提上去了）？ | 为了让装饰器可以**完全透明地转发**。否则战斗循环拿到的是被装饰的 `Combatant`，需要 `dynamic_cast` 下去才能取技能表。用略宽的接口换取调用方全程无向下转型，是刻意的取舍。 |
| 为什么"控制抗性"要有 1 回合免疫？ | 这是实测中真实发现的问题：不做限制时，法师的 `冰火两重天`（100% 冰冻）可以让 BOSS 从头冻到尾、完全无法出手，战斗失去意义。这条规则写在 `CharacterState` 的退出逻辑里，因为它属于"状态自身的行为"。 |
| 为什么 `BerserkState` 免疫控制？ | 同理 —— 否则玩家一个控制技能就能把 BOSS 的爆发期白白拖过去，二阶段设计形同虚设。 |
| 为什么状态类只提供"系数"而不直接操作角色？ | 避免状态类反向依赖 `Character` 造成循环引用，同时保留了状态模式最核心的价值 —— 消除状态判断的 `if-else` 树。 |
| 为什么用抽象工厂而不是工厂方法？ | 工厂方法解决"一个产品的创建延迟到子类"；抽象工厂解决"一整个产品族的一致性创建"。本项目武器、防具、技能必须配套，所以用抽象工厂。 |
| 为什么天赋也要由工厂产出（`applyTalent()`）？ | 因为"职业"的差异不止体现在装备与技能上，还体现在基础数值与伤害规则上。只打印一句天赋说明却不改数值，就是典型的"说明与实现脱节"；把 `talent()`（文案）与 `applyTalent()`（效果）放进同一个工厂，产品族的一致性才是完整的。 |
| 为什么 `applyTalent()` 要作用于裸角色、且在 `equip()` 之前？ | 天赋改的是**基础属性**（`baseAtk_`/`baseDef_`/`critRate_`），装备是在基础属性**之上**做加算（`atk() = baseAtk_ + Σ 装备加成`）。两者层次不同、互不覆盖，但按"基础 → 装饰"的顺序书写语义最清晰，也避开了"天赋写到装饰器上"的歧义。 |

## 五、可扩展方向（答辩备用，说明模式的可扩展性）

| 想加的功能 | 需要做什么 | 需要改动的既有代码 |
|-----------|-----------|------------------|
| 新增职业"牧师" | 新增一个具体工厂类 | **0 行** |
| 新增伤害类型"毒伤" | 新增一个 `DamageStrategy` 子类 | **0 行** |
| 新增"护盾吸收"结算环节 | 新增一个 `DamageHandler` 并插到链上 | **1 行**（链的构造函数） |
| 新增"伤害统计面板" | 新增一个 `IBattleObserver` 实现 | **1 行**（`bus.attach`） |
| 新增"技能树"（连招嵌连招） | 直接用 `ComboSkill::add()` 嵌套 | **0 行** |
| 回合流程分 PvE / PvP | 抽出**模板方法**，派生两个子类 | 中等改动 |
| 战斗回放/悔棋 | 引入**命令模式**把操作对象化 | 中等改动 |

# 游戏战斗与技能系统 —— 设计模式综合演示

《设计模式》课程大作业 · 自拟项目综合实现 · C++17

本项目把课堂上学习的 **8 种设计模式** 落进一个可运行的回合制战斗系统里，
所有模式不是孤立的小例子，而是**在同一个系统内互相协作**：

| # | 设计模式 | 在本项目中的落点 |
|---|---------|-----------------|
| 1 | 单例 Singleton | `GameConfig` —— 全局规则参数与随机数发生器 |
| 2 | 抽象工厂 Abstract Factory | `HeroPackageFactory` —— 战士/法师/射手三套职业产品族 |
| 3 | 策略 Strategy | `DamageStrategy`（物理/魔法/真实伤害）、`AIStrategy`（莽夫/保守/辅助） |
| 4 | 装饰器 Decorator | `EquipmentDecorator` —— 武器、防具、附魔、宝石的逐层包裹 |
| 5 | 观察者 Observer | `EventBus` + 日志/成就/BOSS 阶段/战斗回放四个观察者 |
| 6 | 状态 State | `CharacterState` —— 正常/眩晕/冰冻/狂暴 |
| 7 | 责任链 Chain of Responsibility | `DamageChain` —— 闪避→护甲→格挡→暴击四段结算流水线 |
| 8 | 组合 Composite | `ComboSkill` —— 连招与单体技能的统一调用 |

## 一、编译与运行

### 方式 1：一键脚本（推荐）

Windows（双击或在 cmd 中执行）：

```bat
build.bat
```

Git Bash / Linux / macOS：

```bash
bash build.sh
```

### 方式 2：CMake

```bash
cmake -B build -S .
cmake --build build
./build/GameBattle.exe
```

> **注意（实测踩坑）**：若使用 **MinGW Makefiles** 生成器，工程所在路径**不能含中文**。
> `mingw32-make` 无法正确解析含中文的路径，会报
> `No rule to make target '.../main.cpp'`。
> 此时请改回方式 1，或把工程放到纯英文路径下构建，
> 或改用 Ninja / MSVC 生成器（它们对非 ASCII 路径没有这个问题）。
> 本项目已实测：在纯英文路径下 CMake + MinGW Makefiles 构建与运行均正常。

### 方式 3：直接调用编译器

```bash
g++ -std=c++17 -O2 -Wall -Iinclude \
    src/core/*.cpp src/character/*.cpp src/skill/*.cpp src/equipment/*.cpp \
    src/combat/*.cpp src/observer/*.cpp src/battle/*.cpp main.cpp \
    -o build/GameBattle.exe
```

**编译环境要求**：支持 C++17 的编译器（实测 GCC 15.1.0 / MinGW-w64），无任何第三方库依赖。

> Windows 控制台若出现中文乱码，先执行 `chcp 65001` 切到 UTF-8 代码页。

### 方式 4：控制运行后的窗口行为

直接双击 `build\GameBattle.exe` 时，Windows 会在进程退出的瞬间销毁它新建的控制台窗口，
上百行演示输出还没看清就随窗口一起消失。程序会**自动识别**这种"双击启动"场景并停住等一次回车：

| 启动方式 | 结束时的行为 |
|---------|-------------|
| 双击 `GameBattle.exe` | **停留**，提示 `按 Enter 键关闭窗口 ...` |
| 从已有 cmd / PowerShell / 终端启动 | 不停留（窗口本来就不会消失） |
| 双击 `build.bat` | 脚本在结束时无条件等待按键（`build.sh` 则不停留） |
| 加参数 `--pause` | 强制停留 |
| 加参数 `--no-pause` | 强制不停留（供脚本、管道、重定向调用） |

判断依据是**当前控制台关联的进程数**：双击启动时这个控制台由本进程独占，
从终端启动时至少还有一个父 shell 挂在同一个控制台上。
输出重定向到文件时不受影响 —— `docs/演示输出.txt` 就是重定向抓取的结果。

## 二、预期输出

程序分三幕演示，运行后依次输出：

**第一幕 · 装饰器模式**：打印同一个角色被逐层包装后的面板变化 ——

```
  ① 裸装：示范兵 HP 200/200  ATK 30  DEF 10  伤害类型：物理
  ② 装上巨剑后：示范兵 HP 200/200  ATK 39  DEF 10  暴击率 15%  伤害类型：物理  | 装备：巨剑
  ③ 附加烈焰附魔后：示范兵 HP 200/200  ATK 46  DEF 10  暴击率 15%  伤害类型：魔法  | 装备：巨剑 + 烈焰附魔
  ④ 镶嵌暴击宝石后：示范兵 HP 200/200  ATK 46  DEF 10  暴击率 27%  伤害类型：魔法  | 装备：巨剑 + 烈焰附魔 + 暴击宝石
```

注意第 ③ 步：**只加了一层附魔装饰器，伤害类型就从"物理"变成了"魔法"** ——
这是装饰器模式与策略模式联动的效果。

**第二幕 · 责任链结算轨迹**：把一次攻击经过的四道判定逐环节打印出来 ——

```
  1. 闪避判定：命中
  2. 护甲减伤：按【物理】规则结算 60 vs DEF 30 -> 30
  3. 格挡判定：未触发
  4. 暴击判定：触发暴击 x2 -> 60
```

这段轨迹由 `DamageContext::trace` 在结算过程中真实写入，不是手工构造的示例。

**第三幕 · 完整战斗**：3 名英雄（亚瑟/梅林/莉娜）对抗 4 只怪物（含 BOSS 暗影魔龙），
逐回合输出战斗日志，覆盖暴击、格挡、闪避、眩晕、冰冻、BOSS 二阶段狂暴、连招、成就解锁等全过程。

完整运行输出见 [`docs/演示输出.txt`](docs/演示输出.txt)。

> 程序使用固定随机种子（`20261010`），因此**每次运行的战斗过程完全一致**，
> 便于实验报告截图与答辩复现。

## 四、几个值得注意的设计细节

1. **一条伤害要过四道关**
   一次攻击的结算被拆成 `闪避判定 → 护甲减伤 → 格挡判定 → 暴击判定` 四个环节（责任链），
   任一环节都可以改变结果甚至终止流程（闪避成功直接返回）。
   新增"反伤""护盾吸收"只需实现一个 `DamageHandler` 并挂到链上，既有代码零改动。

2. **控制不会被无限锁死**
   单位从眩晕/冰冻中恢复后，会获得 1 回合"控制抗性"。
   这条规则写在 `CharacterState` 的退出逻辑里，而不是散成技能中的 `if` 判断 ——
   把"状态带来的行为"继续留在状态模式内部。

3. **BOSS 二阶段与战斗逻辑解耦**
   战斗结算代码完全不知道"BOSS 血量过半会狂暴"这件事。
   它由 `BossPhaseObserver` 监听事件后触发 —— 新增一个 `attach()` 就是全部成本。

4. **装饰器透明传递**
   `EquipmentDecorator` 完整实现了 `Combatant` 接口并逐项转发，
   因此"裸角色"与"穿了四层装备的角色"在战斗循环里用法完全一致，
   全程不需要任何 `dynamic_cast`。

## 五、可扩展方向（答辩备用）

- 把 `Battle` 的回合骨架抽成**模板方法**，派生 `PvETurn` / `PvPTurn`
- 增加**命令模式**，把每回合的操作封装成可撤销的对象，实现战斗回放/悔棋
- 增加**外观模式**，用一个 `GameFacade` 收拢"建队 → 开打 → 取战报"三步
- 让 `EventBus` 支持事件优先级与条件订阅
